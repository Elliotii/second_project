# 1. 本文件负责什么

本文件不是新的实施计划，而是第二项目后续所有 Version Charter、Goal Contract、架构设计和代码审查必须遵守的身份约束。

它专门防止两类已经出现过的偏差：

1. **把范围控制误当成项目定位**  
   为了降低当前版本复杂度，逐步把项目压缩成：
   `Pi + Verifier + Trace + Baseline/Candidate + Report`。

2. **把长期路线误当成当前实施授权**  
   因为知道 V2/V3 的方向，提前建设多路径平台、Experience Registry、Router、Curator 或 Promotion Control Plane。

正确原则是：

> 范围控制决定当前先做什么，不决定项目最终只能是什么。

---

# 2. 项目长期身份

第二项目的长期身份是：

> **一个可靠性优先、环境反馈驱动、能够进行有界多路径恢复，并将经过验证的恢复经验逐步沉淀为 Skill、Policy 和 Routing 能力的 Adaptive Coding Agent Harness。**

其核心能力层级是：

```text
可靠执行与可信证据
→ Skill / Runtime 分层比较
→ 有界多路径自适应恢复
→ 受控 Experience Reuse
→ 经验驱动 Routing 与 Scaffolding Retirement
```

---

# 3. 项目不是什么

项目不是：

- Pi 的包装器；
- 单纯 Eval Runner；
- Trace Dashboard；
- Baseline/Candidate 报告平台；
- Claude Code Clone；
- 通用 Multi-Agent Framework；
- 通用 Benchmark SaaS；
- 开放式自动改源码的 Self-Evolving Agent；
- 为了展示架构而提前建设的大型控制平台。

# 4. 不可弱化的项目身份约束

```yaml
project_identity_guardrails:
  V0_is_foundation_not_final_identity: true
  V1_must_compare_skill_and_runtime_control: true
  V2_is_mandatory_portfolio_north_star: true
  verifier_is_feedback_not_project_endpoint: true
  trace_is_evidence_not_primary_product: true
  at_least_one_active_behavior_change_is_required: true
  project_must_remain_a_real_coding_agent: true
  environment_outcome_has_higher_authority_than_model_self_report: true
```

这些约束的含义如下。

## 4.1 V0 是基础版本，不是长期终点

V0 可以只完成：

- Pi Adapter；
- Task / Run / Attempt；
- Workspace；
- Session；
- Journal；
- Verifier；
- Outcome；
- 真实 Coding Run。

但不能因为 V0 足够可用，就重新把项目定义成纯 Reliability Workbench。

## 4.2 V1 必须让 Skill 成为真实竞争者

不能预设 Runtime Control 一定高级。

V1 至少比较：

```text
Baseline
Skill-only
Skill + External Verifier / Runtime Control
```

目标是证明：

- Skill 能解决什么；
- Runtime Control 解决什么；
- 哪些问题只有 Tool、Session、Context、Workspace 或 Verifier 层能解决。

## 4.3 V2 是求职阶段核心目标

V2 的有界多路径恢复不是可有可无的“以后扩展”。

V0/V1 的架构必须能够自然承接：

```text
Primary Attempt
→ Failure
→ Recovery Strategy A / B
→ Isolated Rollout
→ Environment Verification
→ Best Result Selection
```

但不得在 V0 提前实现完整 V2。

## 4.4 Verifier 与 Trace 是反馈基础

Verifier 的价值不是“生成一份成功报告”，而是：

- 判定 Outcome；
- 触发 Recovery；
- 区分 Task Failure 与 Invalid Run；
- 为多路径选择提供硬门；
- 为 Experience 提供可信反馈。

Trace 的价值不是“事件更多”，而是：

- 失败归因；
- 恢复路径比较；
- Experience 来源；
- Candidate Promotion 的证据链。

# 5. 主动能力最低要求

项目完成到 Portfolio-ready 时，必须能够回答：

> 系统介入后，Agent 实际采取了什么不同的行动？

不能只回答：

- 多记录了事件；
- 多输出了一份报告；
- 多跑了一次测试；
- 多保存了一份 JSON。

主动行为变化至少包括一种：

```text
根据环境失败继续原 Session
根据失败重启新 Session
改变 Context Strategy
改变 Skill / Recovery Policy
运行多个候选恢复路径并选择结果
根据历史证据选择 Recovery Strategy
```

---

# 6. 防止项目被压缩成外围实验壳

每个 V0/V1 基础设施模块都必须回答：

```text
它服务哪一个真实使用、V1 实验或 V2 主动能力？
```

建议审查矩阵：

| 模块 | 合理用途 |
|---|---|
| Pi Adapter | 上游隔离、事件可信性、未来多 Attempt |
| Task / Attempt Identity | 真实任务、实验、公平比较 |
| Workspace | 受控执行、未来多路径隔离 |
| Session Link | Continue / Restart / Fork 策略比较 |
| Verifier | Outcome、Recovery Trigger、Path Selection |
| Journal | Failure Attribution、Experience Source |
| Strategy ID | V1 Policy、V2 Recovery Candidate |
| Environment Identity | 回归和跨任务可比性 |
| Regression | Candidate Promotion / Negative Transfer |
| Budget | 防止 Retry / Best-of-N 无界消耗 |

以下表述本身不足以证明模块值得进入 V0：

- “更完整”；
- “更生产级”；
- “以后可能用到”；
- “方便做 Dashboard”；
- “便于扩展成平台”。

如果一个模块只服务报告美观或抽象完整度，应后移。

# 9. Executor、Verifier、Curator 与 Gate 分权

```text
Executor
→ 执行 Coding Task

Verifier
→ 判断环境结果

Curator
→ 提出 Candidate Intervention

Promotion Gate
→ 决定 Candidate 是否生效
```

禁止形成：

```text
Executor 自己执行
→ 自己判断成功
→ 自己总结经验
→ 自己修改 Verifier
→ 自己批准发布
```

受保护边界包括：

- Task Acceptance Criteria；
- Verifier；
- Gold / Benchmark；
- Permission Upper Bound；
- Cost Guardrail；
- Promotion Threshold。

---

# 10. Skill、Policy、Memory、Patch 的边界

| 对象 | 含义 | 示例 |
|---|---|---|
| Skill | 可复用的过程与约束 | test-first、minimal-patch |
| Runtime Policy | Harness 强制执行的控制逻辑 | Completion Gate、Recovery Budget |
| Context Policy | 如何选择、压缩和外置上下文 | Tool Result Artifact |
| Tool Policy | Timeout、Cancellation、Result Budget | Shell Timeout |
| Memory / Experience | 来自历史 Run 的结构化记录 | 某 Failure Family 的恢复证据 |
| Runtime Patch | 修改核心执行代码 | Pi Adapter 或 Tool Wrapper 修改 |

禁止将所有问题都转成 Skill。

例如：

- Tool Timeout 不是单纯 Skill 问题；
- Verifier 损坏不是 Skill 问题；
- Session Resume 重复副作用不是 Skill 问题；
- Context 丢失关键约束可能是 Context Policy 问题。

# 11. 版本级身份约束

## 11.1 V0

目标：

```text
真实可用、可验证、可追踪的 Coding Agent Workbench
```

不得宣称：

- Adaptive Recovery 已完成；
- Experience Reuse 已完成；
- Self-evolving Harness 已完成。

## 11.2 V1

目标：

```text
验证 Skill 与 Runtime Control 的真实边界
```

必须允许 `INCONCLUSIVE`，不得为了证明 Runtime 优势选择偏置任务。

## 11.3 V2

目标：

```text
Failure-aware Bounded Multi-path Adaptive Recovery
```

要求：

- 失败触发；
- 候选有界；
- Workspace 隔离；
- Environment Outcome；
- 成本约束；
- 首次成功不分支。

## 11.4 V3

目标：

```text
Experience
→ Candidate Intervention
→ Related Task
→ Regression
→ Promote / Reject
```

要求：

- 同任务重跑不够；
- 必须检查相关任务泛化；
- 必须检查无关任务回退；
- Candidate 不自动发布。

# 13. Goal 进入标准

一个问题只有同时满足以下条件，才应升级为正式 Goal：

```yaml
goal_entry_gate:
  blocks_current_version_decision: true
  threatens_core_project_loop: true
  has_concrete_or_highly_specific_evidence: true
  cannot_be_safely_deferred: true
  has_bounded_scope_and_stop_condition: true
```

不能因为：

- 某论文提到；
- 某成熟 Agent 有；
- 某风险理论上存在；
- 为了“生产级”；
- 为了完整覆盖 JD；

就自动创建 Goal。

# 14. 真实使用优先级

项目必须始终保持一个可运行 Coding Agent 产品面。

V0 期间应持续使用真实微型仓库验证：

- 是否能理解任务；
- 是否能读写文件；
- 是否能运行测试；
- 是否能生成合理 Diff；
- CLI 是否可用；
- 报告是否能解释结果。

不能等所有 Contract、Schema、Journal 和 Report 完成后才第一次真实使用。

---

# 15. 证据纪律的边界

G005 已证明 Observer 与 Journal 失效会污染结论，因此关键证据必须可靠。

但不能把“证据纪律”扩张成：

- 记录所有内部状态；
- 每个字段都有独立 Gate；
- 每个小模块一份正式报告；
- 为了证明完整性推迟真实功能。

原则：

```text
关键结论必须可复核
不等于
所有内部细节都必须产品化
```

# 17. 暂停条件

出现以下情况必须暂停：

- V2 被降级成普通可选扩展；
- V0 被定义成项目最终身份；
- 数据模型被写死为两组 Pair；
- 为未来 V3 建立大型 Repository / Service；
- Agent 可以修改 Verifier 或 Promotion Gate；
- 为强调个人贡献拒绝合理成熟模块；
- 为范围控制删除主动能力；
- 为架构完整性增加没有真实用途的抽象层；
- 真实任务使用被持续推迟；
- 项目主要输出变成报告而不是 Coding Agent 行为改变。

---

# 18. 最终约束

第二项目必须同时满足两个方向：

```text
当前版本足够小、可完成、可验证
+
长期路线足够强，不被压缩成外围实验壳
```

正确的演进关系是：

```text
V0 可靠基础
→ V1 Skill / Runtime 边界
→ V2 主动多路径恢复
→ V3 受控经验复用
```

而不是：

```text
V0 建设更多 Trace / Report
→ V1 建设更多 Eval 平台
→ V2 继续建设外围控制面
```
