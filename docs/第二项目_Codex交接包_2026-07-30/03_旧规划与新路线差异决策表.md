# 1. 本文件负责什么

本文件对照：

1. G006 关闭后 Codex 主 Session 形成的旧后续规划；
2. 最新形成的 V0–V5 完整版本化路线；
3. 当前已经固定的 G001–G006 工程事实。

它逐项判断旧规划内容属于：

```text
accepted
modified
superseded
deferred
still_open
rejected
```

本文件的目的不是否定旧规划。旧规划在以下方面仍然是高质量基础：

- Pi 源码事实；
- G001–G006 阶段结论；
- Direct `AgentHarness` 判断；
- Observer / Journal / Invalid Evidence 经验；
- Verifier、Workspace、Session 和 Outcome 边界；
- Goal 治理和证据纪律。

需要更新的是：

- 项目长期身份；
- Portfolio 终点；
- Skill 与 Runtime 的比较；
- V2 有界多路径恢复的地位；
- Experience Reuse 的长期位置；
- V0 数据模型与模块优先级。

# 6. V0 Charter 与最小 Workbench 对照

## 6.1 旧 V0.1–V0.4 的总体处理

旧规划提出：

```text
V0.1 Contracts / CLI / Workspace
V0.2 Execution / Session / Journal
V0.3 Completion Verification
V0.4 Report / Real Use
```

该结构总体保留，但需要三个修正：

1. **V0 不以完整实验平台为目标**；
2. **真实使用不能只放在最后，必须持续验证 CLI 和 Coding Agent 可用性**；
3. **基础数据模型不能写死为只能进行 Baseline/Candidate Pair**。

## 6.2 V0 模块逐项决策

| 模块 | 旧规划 | 新路线判断 | 决策 | 实现约束 |
|---|---|---|---|---|
| CLI `run` | 必须 | 必须 | `accepted` | 优先支持真实单任务使用 |
| CLI `compare` | 必须 | V1 需要 | `accepted` | 不要求 V0 首个 Goal 就完整 |
| CLI `inspect` | 必须 | 有价值但容易膨胀 | `modified` | 只提供必要 Artifact 导航，不做大型 Inspector |
| Task Manifest | 必须 | 必须 | `accepted` | 建议统一叫 `TaskSpec` |
| Run ID | 必须 | 必须 | `accepted` | 保持稳定 |
| Attempt ID | 旧规划有 Run/Attempt 概念 | 未来多路径必需 | `accepted` | V0 应作为一级身份 |
| Variant | Baseline/Candidate | 仍可作为实验标签 | `modified` | 不应成为唯一根数据模型 |
| Strategy ID | 未明确 | V1/V2 必需 | `modified` | V0 可保留可选字段，不实现策略引擎 |
| Parent Attempt ID | 未明确 | V2 路径来源必需 | `modified` | V0 可选字段，默认空 |
| Workspace Identity | 必须 | 必须 | `accepted` | 后续用于 Rollout 隔离 |
| Session Link | 必须 | 必须 | `accepted` | 后续用于 Session 策略比较 |
| Environment Identity | 部分存在于 Source/Artifact Identity | V3 回归可比性必需 | `modified` | 只冻结最小版本/命令/Verifier 标识 |
| Journal v2 | 必须 | 必须 | `accepted` | 不追求记录所有内部状态 |
| Budget Counter | 必须 | 必须 | `accepted` | Token、Latency、Cost、Tool Calls 足够 |
| External Verifier | 必须 | 必须 | `accepted` | 作为受保护边界 |
| Completion Gate | V0.3 核心 | V1 正式比较对象 | `modified` | V0 可实现机制；效果结论属于 V1 |
| JSON Report | 必须 | 必须 | `accepted` | 机器可读优先 |
| Markdown Report | 必须 | 有价值 | `accepted` | 只呈现关键判断 |
| 大型 Run Inspector | 候选 | 非甜点 | `deferred` | 除非真实使用证明必要 |
| SQLite | 非 V0 | 继续非 V0 | `accepted` | 文件 Artifact 足够时不引入 |
| Web UI | 非 V0 | 继续非 V0 | `accepted` | 不为展示提前实现 |

## 6.3 数据模型修正

旧规划容易形成：

```text
PairManifest
├── Baseline
└── Candidate
```

新的最小内部结构应更接近：

```text
Task
└── Run
    ├── Attempt
    │   ├── Strategy
    │   ├── Workspace
    │   ├── Session
    │   └── Outcome
    └── Attempt
```

实验层仍可以声明：

```text
comparison_group:
  - baseline
  - skill_only
  - external_control
```

但 `baseline/candidate` 不应成为不可扩展的底层类型。

### 当前 V0 只需保留的未来安全字段

```yaml
future_safe_identity:
  run_id:
  attempt_id:
  parent_attempt_id: optional
  strategy_id: optional
  workspace_id:
  session_id:
  environment_id:
  verifier_id:
  outcome:
```

### 当前禁止提前实现

- Candidate Registry；
- Rollout Scheduler；
- Path Scoring Engine；
- Experience Repository；
- Promotion Service；
- Router。

# 7. 第一条正式实验路线对照

## 7.1 旧实验

```text
Baseline
vs
Completion Verification Candidate
```

问题：

- 无法区分流程提醒与 Runtime Control 的贡献；
- 无法回答“为什么不用 Skill”；
- Candidate 可能只是获得额外一次调用；
- G006 首次通过已经显示激活率可能较低。

## 7.2 新 V1 实验

```text
A. Baseline
B. Skill-only
C. Skill + External Verifier + Completion Gate
```

| 设计项 | 决策 |
|---|---|
| Completion Verification 仍是第一 Runtime Policy | `accepted` |
| 增加 Skill-only 组 | `modified`，必须加入 |
| Baseline/Candidate 两组固定结构 | `superseded` |
| 一次有界 Recovery | `accepted`，属于 C 组 |
| 用环境 Outcome 而非模型自评 | `accepted` |
| 固定任务与配对公平性 | `accepted` |
| Invalid Run 分开报告 | `accepted` |
| 样本不足允许 `INCONCLUSIVE` | `accepted` |

## 7.3 V1 必须回答的新问题

1. Reliability Skill 已经解决多少正常流程问题？
2. External Verifier 带来什么不可由 Skill 替代的增量？
3. Recovery 收益是否只是额外模型调用带来的？
4. 哪些 Failure 属于 Context、Tool、Session 或 Infrastructure，而不是 Prompt/Skill？
5. Completion Policy 是否值得进入 Active Policy？

# 8. Pilot Eval 对照

- 6–10 个 TypeScript Task；
- 每个 3–5 个配对 Trial；

## 8.2 新路线处理

# 9. V2 有界多路径恢复对照

## 9.1 旧规划中的位置

旧规划没有把多路径恢复列为 Portfolio 核心版本，主要停留在：

```text
首次 Verifier 失败
→ 同一 Session 一次结构化反馈
→ Final Verifier
```

## 9.2 新路线中的位置

```text
Primary Run
→ Verifier Failure
→ Failure Classification
→ 少量恢复策略
→ 隔离 Rollout
→ 环境验证
→ Best Path Selection
```

### 决策

```yaml
V2_bounded_multi_path_recovery:
  status: mandatory_portfolio_north_star
  current_implementation_authority: false
  V0_design_relevance: limited_identity_and_adapter_continuity
```

## 9.3 第一版 V2 的范围

只比较两条路径：

```text
Path A:
  Continue Same Session
  + Structured Failure Packet

Path B:
  New Clean Session
  + Original Task
  + Failure Packet
  + test-first / minimal-patch Skill
```

暂不自动加入：

- 多模型大规模 Best-of-N；
- 无限 Candidate；
- Multi-Agent；
- 学习型 Router；
- 自动生成任意 Workflow。

## 9.4 V0 必须为 V2 保留什么

- Attempt 一级身份；
- Parent Attempt 可选关系；
- Strategy ID；
- Workspace Identity；
- Session Identity；
- 独立 Outcome；
- Pi Adapter 不把单 Session 写死；
- Verifier 可作用于每个 Attempt。

## 9.5 V0 不应为 V2 提前实现什么

- 多 Workspace 调度；
- Worktree 池；
- Path Scoring；
- Selection UI；
- Candidate Generator；
- Branch Merge；
- 自动 Commit 最佳结果。

# 10. Fault 与 Reliability Case 对照

## 10.1 旧规划

旧规划将真实使用、Fault 和 Regression 放在 Completion Pilot 之后，并列出：

- Session Resume；
- Crash-after-side-effect；
- Cancellation；
- Context Compaction；
- Tool Result Budget。

## 10.2 新路线

Fault 分成两类：

### 当前事实和证据基础

- Observer / Journal Invalid Evidence：G005 已真实发生；
- Build / model-data Boundary：G002 已真实发生。

它们保留为工程经验，不必发展成大型 Fault 平台。

### V2.5 主动 Reliability Case

优先：

1. Long-running Shell Timeout / Cancellation；
2. Oversized Tool Result / Context Pressure；
3. Session Restart / Side-effect Reconciliation，仅在有真实复现后进入。

## 10.3 决策表

| 风险 | 旧位置 | 新位置 | 决策 |
|---|---|---|---|
| Tool Result Budget | 第二 Policy 首选 | V2 Strategy 或 V2.5 Context Case | `modified` |
| Context Compaction | 条件风险 | Context Strategy / Fault Case | `modified` |
| Cancellation | 条件风险 | V2.5 高价值候选 | `modified` |
| Crash-after-side-effect | 条件风险 | 真实 Case 触发 | `accepted` |
| Settled Resume | 条件风险 | H2 Reliability，按使用触发 | `accepted` |
| 通用 Fault Injection 平台 | 不做 | 继续不做 | `accepted` |
| 通用 Durable Runtime | 不做 | 继续不做 | `accepted` |
| Exactly-once 平台 | 不做 | 继续不做 | `accepted` |

# 11. Experience、Skill 与 Policy 生命周期对照

## 11.1 旧规划

旧规划中的 Experience 主要通过：

```text
真实使用 Failure
→ 人工确认
→ Regression Case
→ Policy Promote / Revise / Reject
```

这一闭环有价值，但尚未明确区分：

- Trace；
- Diagnosis；
- Experience；
- Candidate Skill；
- Active Policy。

## 11.2 新路线

明确数据链：

```text
Raw Trace
→ Failure Diagnosis
→ Experience Record
→ Candidate Intervention
→ Related Task Evaluation
→ Regression
→ Promote / Reject / Rollback
```

## 11.3 决策表

| 主题 | 决策 | 说明 |
|---|---|---|
| 真实 Failure 进入 Regression | `accepted` | 继续保留 |
| Failure Candidate 需要人工确认 | `accepted` | 防止错误 Gold |
| Skill 成为一级实体 | `modified` | 但不是所有 Experience 都变成 Skill |
| Candidate 类型只允许 Skill | `rejected` | 还可能是 Context/Recovery/Tool/Router |
| Executor 自己批准 Skill | `rejected` | Verifier、Curator、Promotion Gate 分权 |
| Curator 是复杂 Multi-Agent | `deferred` | 初期只是受限结构化模型调用 |
| Experience Repository | `deferred` 到 V3 | V0 不实现 |
| Related Task Stream | `modified`，V3 必须 | 防止同任务记忆 |
| Unrelated Regression | `modified`，V3 必须 | 检查负迁移 |
| Promotion / Rollback | `accepted`，V3 最小闭环 | 不建大型控制平台 |
| Skill insert/update/delete | `deferred` | V3 只需最小生命周期 |
| Automatic Harness Source Rewrite | `rejected` 作为求职前目标 | 长期研究上限而非路线要求 |

allowed_reuse:

# 17. Goal 治理对照

## 17.1 继续有效

- 主 Session 负责范围、决策、Contract 和验收；
- 专用 Goal Session 负责执行和报告；
- 未授权不得调用模型、修改 Pi 或提交 Git；
- Goal 必须有 Pass / Fail、Pause Condition 和非目标；
- 发现证据无效必须停止，不能回填。

## 17.2 需要减轻的部分

旧过程出现过较高治理开销。

新的治理原则：

```text
每个 Version：
  一份 Version Charter
  → 1–3 个有界 Goal
  → Closeout
```

不需要：

- 每个普通依赖一个 ADR；
- 每个未验证风险一个 Goal；
- 每个内部 Schema 一份正式报告；
- 为证明“完整性”无限增加 Gate。

### 决策

| 主题 | 决策 |
|---|---|
| 主/专用 Session 分工 | `accepted` |
| 所有小风险都需 Goal | `rejected` |
| 所有外部来源都需全面审计 | `rejected` |
| 关键架构与证据需 ADR/Report | `accepted` |
| 每版本 1–3 个有界 Goal | `modified` |
| 用户单独授权真实模型和 Commit | `accepted` |

# 22. 最终结论

旧规划的底层工程判断和证据治理继续构成 V0 的可靠基础。

新路线没有推翻：

```text
Pi
+ Adapter
+ Workspace
+ Session
+ Journal
+ Verifier
+ Outcome
```

它改变的是这些基础设施最终服务的对象：

```text
旧：
验证和管理一条固定 Harness Policy

新：
先验证 Skill 与 Runtime 的真实边界，
再支持失败感知的有界多路径恢复，
最后把经过验证的恢复经验沉淀为可治理的 Candidate Intervention。
```

因此，Codex 后续不能：

1. 把新路线解释为立即实现 V2/V3；
2. 继续把 V2 降级成可选扩展；
3. 为未来提前创建大规模抽象平台；
4. 为了强调个人贡献而拒绝合理移植成熟模块；
5. 把 Verifier、Trace 和 Report 本身当成项目最终产品身份。

正确的下一步仍然是：

```text
读取本交接包
→ 完成 Roadmap Reconciliation
→ 完成 Reference Acquisition Plan
→ 起草 V0 Version Charter
→ 等待用户审查
```
