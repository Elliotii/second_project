## 5. Main Session 更换触发条件

保留当前主 Session，除非出现以下任一情况：

1. 用户明确要求更换主 Session；
2. 当前主 Session 无法可靠继承 Charter、事实和决策历史；
3. 连续出现把未来愿景当当前事实、越权实现或丢失用户决定的情况；
4. 上下文损坏且无法通过 `CURRENT_STATE`、Charter、Contract、Closeout 和本文件恢复；
5. 项目需要独立架构审计，用户决定让新 Session临时或永久承担主审；
6. 当前主 Session 因工具/环境故障无法继续。

以下情况不自动触发更换：

- 普通上下文压缩；
- 创建一个专用 Goal Session；
- 某个 Goal 命中 Pause Condition；
- 需要一个有界研究 Session；
- 专用 Session 的实现报告需要主 Session复核。

更换时，新主 Session 必须先读：

```text
CURRENT_STATE.md
V0_VERSION_CHARTER.md
09_对接执行、文件权威与验收规则.md

最近 accepted Report / Closeout

```

## 8. 后续标准 Goal 流程

```text
主 Session 研究并起草 Goal Contract
→ 用户审查 Contract
→ 用户接受 Contract
→ Contract 正式化，但仍未执行
→ 用户单独授权 Goal Activation 和 Control Baseline Commit
→ 主 Session 更新 CURRENT_STATE、Contract 状态和必要控制文件
→ 主 Session 创建并核验干净的 Control Baseline Commit
→ 主 Session 记录 Baseline Commit
→ 主 Session 生成专用 Goal Session 启动 Prompt
→ 新专用 Session 从该 Commit 开始核验 Gate A
→ 实现、运行 Gates、保存 Evidence
→ 专用 Session 提交 Report / Closeout Draft / CURRENT_STATE_UPDATE_PROPOSAL 并停止
→ 主 Session 复核 source delta、命令和证据
→ 用户决定 Accept / Revise / Reject
→ 用户另行授权 Commit、状态同步或下一 Goal
```

合同接受不等于激活；Activation 必须由用户单独授权。正式执行必须从已提交 `active_goal: V0_A`（或对应 Goal ID）的干净 Control Baseline Commit 开始。不得先提交 `active_goal: null` 的 baseline，再用未提交控制变更启动 Goal。Activation 不自动包含真实模型、额外 Run、Pi patch、外部下载或实现结果 Commit 权限。
