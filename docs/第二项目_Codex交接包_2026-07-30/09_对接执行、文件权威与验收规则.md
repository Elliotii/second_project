### Current V1-C mechanical-error and restart clarification

- A command/path error that occurs before Credential resolution, Pilot state,
  network dispatch, Provider/model use, or evidence mutation is a recoverable
  Main-orchestration defect. Correcting it does not consume a Run and does not
  itself force Goal closeout.
- An error after a sensitive/product boundary remains subject to the existing
  fail-closed Pause Conditions.
- The historical four-Run prefix is immutable and remains useful diagnostic
  evidence, but it is excluded from the restarted formal comparison.
- The corrected 24-cell Pilot uses a new Manifest ID and disjoint Pilot root;
  old artifacts must never be overwritten, merged, or silently reclassified.
- The comparison objective remains Baseline versus Skill-only versus Skill +
  Runtime Control. Closeout is permitted only after a valid aggregate or a
  material non-recoverable Pause Condition, not because of a zero-side-effect
  shell or path typo.

#### 4.6.1 Goal 模式的开启与目标

- Goal 模式只在用户明确要求或授权后开启；用户也可以在客户端手动使用 `/goal`；
- Main Session Goal 必须写 Outcome、Constraints 和 Verification，并直接绑定 Version Question；
- 专用 Session Goal 只绑定它负责的有界子目标，不得把自己的完成解释成 Version 完成；
- Goal 模式不自动获得源码、网络、Credential、模型调用、Git Commit、Pi Patch 或架构变更权限；
- Main Session不得把“完成所有 V2/V3 工作”这类无边界活动描述直接作为 Goal；
- Version Question 未取得有效证据时，不得仅因某个 Goal/Stage DoD 通过而 Closeout；只有用户明确接受 revised/inconclusive closeout 才能例外。

#### 4.6.2 软复杂度预算

Session、Correction、Audit、Report、Commit 和 Goal 数量只作为默认设计预算，不作为
硬停止或完成条件。超过默认预算时必须先做 Complexity Checkpoint，但不得因此：

- 丢弃尚未完成的版本比较；
- 把缺少证据解释成 Pass；
- 自动关闭 Goal 或 Version；
- 忽略仍在 Contract 范围内且可安全修复的问题；
- 为避免讨论而接受不完整结论。

硬停止继续只用于安全、权限、不可逆副作用、真实成本/运行预算、证据身份失效，或
必须由用户选择的架构/范围分叉。

#### 4.6.3 Complexity Checkpoint

当用户提出“是不是变复杂了”“做一次复杂度检查”“这个 Session 是否必要”等提醒，
或出现第二个 material correction/audit、新 Goal、新子系统、新依赖、范围明显扩张时，
Main Session先在对话中提交：

```yaml
version_question:
current_stage:
evidence_already_obtained:
evidence_still_missing:
new_work:
  required_now:
  safely_deferred:
  rejected:
proposed_session:
  exact_question:
  why_existing_evidence_is_insufficient:
  decision_it_can_change:
  stop_condition:
route_options:
recommendation:
effect_on_version_completion:
```

默认不为该检查新建 Markdown、Commit 或专用 Session。复盘结果可以是继续当前路线、
合并返修、缩小实验、拆分 Goal、修改 Contract，或在用户明确同意后接受 inconclusive；
“流程次数较多”本身不是停止选项。

#### 4.6.4 专用 Session 建议过滤

专用 Session 报告必须把内容分成：

```text
A. Assigned-question findings
B. Non-binding additional observations
```

B 类观察只有同时满足以下条件才可改变当前路线：

1. 对应当前 Contract 或 Version Question；
2. 有具体、可复现证据；
3. 阻塞当前版本核心结果；
4. 不能安全延后。

否则 Main Session必须将其 `defer`、`known_issue` 或 `reject`。专用 Session不得凭一个
推测性风险自动触发新的 Research Session、Audit、Goal、Gate、依赖或平台模块。

V2 默认维持：Main 规划/Contract → 一个 Implementation Session → Main 轻量验收 →
风险成立时一个 focused Audit → 原 Implementation Session 接收合并返修 → 一个冻结且
no-source-edit 的 Real Execution Session → Main 验收正例、反例和 Version Question。
需要继续返修时先复盘，不因默认次数用尽而停止。

V3 默认只完成一条：真实失败 → grounded diagnosis → 一个 typed Candidate Intervention
→ original/related/held-out/unrelated 验证 → 人工 Promote 或 Reject。不得为了“完整”同时
建设 Experience 平台、Router、全类型 Curator、自动源码修改或大规模 Benchmark。

## 5. Main Session 更换触发条件

1. 用户明确要求更换主 Session；
2. 当前主 Session 无法可靠继承 Charter、事实和决策历史；

- 创建一个专用 Goal Session；
