# 2. V0 的一句话定义

> **V0 是一个基于固定 Pi Direct `AgentHarness` 的、可实际运行 Coding Task、可控制 Workspace、可关联 Session 与事件、可由外部环境 Verifier 判断 Outcome，并能保留可复核运行证据的最小 Coding Agent Workbench。**

V0 的目标是：

```text
把 G001–G006 的 Spike 与研究证据
转化为一个可以真实使用、测试和扩展的正式项目基础
```

V0 不是：

```text
完整 Adaptive Recovery
完整 Experience Reuse
完整 Eval Platform
完整 Durable Runtime
完整 Sandbox
完整 Web 产品
```

# 4. V0 的产品定位

V0 必须是一个真实可用的 Coding Agent Workbench，而不是只服务实验的脚本集合。

至少应能支持以下自然任务：

- 读取一个小型 TypeScript 仓库；
- 理解一个明确 Coding Task；
- 搜索和读取文件；
- 修改允许路径内的代码；
- 运行测试、Build 或 Type Check；
- 生成可检查的 Git Diff；
- 由外部 Verifier 判断任务结果；
- 保存 Run、Session、Tool、Verifier 和 Outcome 证据；
- 让用户从 CLI 查看关键结果。

V0 不要求完成复杂 IDE、TUI 或 Web UI。

# 6. V0 必做能力

以下是 V0 Charter 应包含的最小能力集合。

## 6.1 Pi Direct Adapter

必须：

- 通过公共 emitted API 使用 `AgentHarness`；
- 集中处理 Pi 构造、配置和事件订阅；
- 使用已验证的 `subscribe()` 路线；
- 不让上层模块直接依赖 Pi 内部事件细节；
- 记录 Pi Commit / Package Version；
- 默认不修改 Pi Core。

建议接口只暴露本项目需要的最小能力：

```ts
interface AgentRuntimeAdapter {
  run(input: RuntimeRunInput): Promise<RuntimeRunResult>;
  abort(reason?: string): Promise<void>;
}
```

最终接口由 Codex 基于真实源码起草，不要求照抄此示例。

---

## 6.2 TaskSpec

V0 至少定义：

```yaml
task_spec:
  task_id:
  title:
  instruction:
  repository_or_fixture:
  allowed_paths:
  forbidden_paths:
  setup_commands:
  verifier_config:
  budget:
```

Codex 可以调整字段，但必须满足：

- 可复现；
- 可验证；
- 副作用边界明确；
- 不把模型自评当成成功；
- 不把未来 Experience 字段提前塞入。

---

## 6.3 Run 与 Attempt

V0 必须区分：

```text
Task
Run
Attempt
```

建议语义：

- `Task`：要解决的问题和环境合同；
- `Run`：一次完整工作台执行或比较；
- `Attempt`：一个具体策略、Session 和 Workspace 下的执行。

V0 即使只执行一个 Attempt，也不应将内部模型写死为：

```text
Baseline
Candidate
```

建议最低字段：

```yaml
attempt:
  attempt_id:
  run_id:
  parent_attempt_id: null
  strategy_id: optional
  workspace_id:
  session_id:
  environment_id:
  verifier_id:
  status:
  outcome:
```

`parent_attempt_id` 与 `strategy_id` 可在 V0 中为空，但应避免未来 V2 大改。

---

## 6.4 Workspace

V0 必须支持：

- 从明确 Fixture 或 Repository 创建受控 Workspace；
- 记录初始状态；
- 设置 CWD 和环境；
- 限制允许/禁止路径；
- 在 Run 后保留或清理；
- 生成最终 Diff 或状态摘要。

V0 Charter 必须决定：

- 临时目录还是 Git Repository Fixture；
- 是否需要 Git Worktree；
- 成功修改如何导出；
- 失败 Workspace 是否保留；
- 初始状态如何比较。

V0 不需要多路径 Workspace 调度器。

---

## 6.5 Session Link

V0 必须：

- 创建或关联 Pi Session；
- 将 `run_id` / `attempt_id` 与 Session 关联；
- 保存 Session 路径或 ID；
- 在报告中可追踪；
- 区分 Agent Transcript 与 Workbench Run State。

V0 不要求：

- 跨进程 Resume；
- Session Fork；
- in-flight Tool 恢复；
- Durable Runtime。

---

## 6.6 Event Journal

V0 必须延续 G006 Journal v2 的闭合 Envelope 原则：

```text
schemaVersion
seq
timestamp
type
runId
attemptId
sessionId
data
```

可以按真实需求调整，但必须：

- 外层事件身份不可被业务 payload 覆盖；
- Provider、Message、Tool、Settled、Verifier、Outcome 可关联；
- Observer 故障可产生 Invalid Run；
- Secret 与完整 Reasoning 正文不得持久化；
- 不追求记录所有内部状态。

---

## 6.7 External Verifier

V0 必须定义统一 Verifier Contract。

首批候选：

- Test Command；
- Build；
- Type Check；
- 文件存在或内容断言；
- Git Diff；
- Forbidden Path；
- Task-specific Assertion。

必须区分：

```text
Task Success
Run Validity
Verifier Validity
```

例如：

```yaml
verification:
  verifier_status: valid | invalid
  task_status: passed | failed | unconfirmed
  violations:
  evidence:
```

V0 不应把 LLM Judge 作为硬 Outcome 权威。

---

## 6.8 Outcome 与 Invalid Run

V0 Outcome 类别应保持少量、清晰。

建议候选：

```text
passed
task_failed
agent_failed
infrastructure_invalid
verifier_invalid
cancelled
budget_exhausted
unconfirmed
```

Codex 可以调整命名，但必须满足：

- Observer / Journal 故障不计为 Agent Failure；
- Verifier 自身错误不计为 Task Failure；
- Provider / Tool / Workspace 基础设施错误可独立归因；
- 无充分证据时允许 `unconfirmed`；
- Invalid Run 不混入 Policy 效果统计。

---

## 6.9 Budget

V0 至少记录：

- Provider Request；
- Token；
- Latency；
- Cost；
- Tool Call；
- Recovery Count；
- 总运行时间。

V0 只需实现基础 Guardrail，不做复杂预算优化器。

---

## 6.10 CLI 与结果输出

V0 推荐最小命令：

```text
workbench run
workbench inspect
```

`compare` 可以进入 V0 后半段或 V1，Codex 应根据 Goal 切分决定。

结果输出：

- JSON 机器报告；
- Markdown 人类报告；
- Artifact 路径索引；
- 最终 Workspace / Diff；
- Session / Journal / Verifier Link。

`inspect` 只需导航关键 Artifact，不做大型交互式平台。

# 9. V0 为 V1 保留的连续性

V1 将比较：

```text
A. Baseline
B. Skill-only
C. Skill + External Verifier / Runtime Control
```

因此 V0 应保留：

- Strategy / Configuration Snapshot；
- Skill Bundle Identity；
- Verifier Identity；
- Model / Thinking Identity；
- 相同 Task / Workspace 初始化；
- Attempt 独立 Outcome；
- Token / Latency / Cost；
- Invalid Run 分类。

V0 不需要提前实现完整实验调度平台。

---

# 10. V0 为 V2 保留的连续性

V2 是 Portfolio North Star：

```text
Primary Attempt
→ Failure
→ Recovery Strategy A / B
→ Isolated Rollout
→ Environment Verification
→ Best Result Selection
```

V0 只需为此保留：

```yaml
V2_continuity:
  attempt_is_first_class: true
  parent_attempt_id_optional: true
  strategy_id_optional: true
  workspace_identity: required
  session_identity: required
  verifier_per_attempt: required
  outcome_per_attempt: required
  adapter_not_single_session_hardcoded: true
```

V0 不应提前实现：

- 多 Workspace；
- Candidate Scheduler；
- Path Score；
- Merge；
- 自动 Commit 最佳结果。

# 11. 真实使用要求

V0 不能等全部基础设施完成后才第一次真实使用。

建议每个实现 Goal 都至少包含一个真实或接近真实的微型 Coding Task：

```text
读取仓库
→ 修改代码
→ 运行环境命令
→ Verifier
→ 查看 Diff
```

至少覆盖：

- Bug Fix；
- 小功能；
- 测试；
- Build / Type Check。

真实使用的目的不是在 V0 估计统计提升，而是验证：

- CLI 可用；
- Tool Profile 足够；
- System Prompt 合理；
- Workspace 行为正确；
- 结果 Artifact 可解释。

# 20. 暂停条件

Codex 在起草 Charter 时发现以下情况必须暂停：

# 22. 最终原则

V0 必须同时做到：

```text
足够小
足够真实
足够可靠
足够可扩展
```

其中“可扩展”只意味着：

- 数据身份不走死路；
- Adapter 边界合理；
- V1/V2 不需要推翻核心结构。

它不意味着现在建设未来平台。

正确关系是：

```text
V0：
真实 Coding Agent Workbench

V1：
Skill / Runtime / Verifier 边界

V2：
有界多路径自适应恢复

V3：
受控 Experience Reuse
```

V0 的成功标准不是“未来都已经抽象好”，而是：

> **当前可以真实运行和验证，同时不会阻碍后续主动 Harness 能力。**
