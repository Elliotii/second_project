# 1. 本交接包的目的

本交接包用于把第二项目在 G006 之后的工程事实，与最新形成的完整版本化路线重新对齐。

它要解决的不是“立刻开始下一轮开发”，而是以下四件事：

1. 保留 G001–G006 已形成的源码、动态实验和证据结论；
2. 明确第二项目的长期身份已从较窄的 Reliability / Eval Workbench，升级为 Reliability-first Adaptive Coding Agent Harness；
3. 区分当前版本授权、求职阶段核心目标和长期扩展方向；
4. 为后续 V0 Version Charter 提供一致、可审计的输入。

当前交接只授权：

```text
阅读
→ 对照
→ 发现冲突
→ 形成分析与 Charter 草案
```

当前交接不授权：

```text
修改源码
创建新 Goal
激活 Goal
创建正式 workbench/
调用真实模型
追加 Attempt
修改 Pi Core
修改 CURRENT_STATE.md

直接实现 V1 / V2 / V3
```

# 2. 本交接包不是什么

本交接包不是：

- 对 G001–G006 工程事实的重写；
- 对固定 Pi 源码结论的推翻；
- V2–V5 的当前实施命令；
- 全面重新研究 Agent Harness 市场的授权；
- 要求从零重写 Pi 已有能力；
- 要求只做抽象借鉴而禁止移植成熟模块；
- 要求为了控制范围，把项目永久缩小为 Trace / Verifier / Report 平台。

# 3. 项目当前的三层方向

后续所有文件都必须区分以下三个层级。

## 3.1 当前执行层

当前下一阶段是：

```text
Phase 4
→ 起草并审查 V0 Version Charter
```

只有经用户接受的 V0 Charter 和后续 Goal Contract，才能授权正式实现。

## 3.2 求职阶段核心目标

V2：

```text
Failure-aware Bounded Multi-path Adaptive Recovery
```

即：

```text
Primary Run
→ Environment Verification
→ Failure Classification
→ 少量候选恢复路径
→ 隔离 Rollout
→ 环境验证与成本约束
→ 最佳结果选择
```

V2 是第二项目的 Portfolio North Star，不是可有可无的远期装饰。

## 3.3 长期演进方向

V3：

```text
Run Trace
→ Failure Diagnosis
→ Experience Record
→ Candidate Intervention
→ Related Task / Regression
→ Promote / Reject / Rollback
```

V3 是明确的后续架构方向，但当前未授权实现。

V4、V5 分别是：

- Experience-guided Routing / Policy Retirement；
- Godot / 游戏研发 AI 工具链 Adapter。

它们属于长期可选扩展，不构成当前 V0 的实现要求。

# 5. 权威优先级

发生冲突时，必须使用以下顺序：

```text
固定源码 / 测试 / 实际命令
    ↓
CURRENT_STATE / 已接受 Goal Closeout / 已接受 ADR
    ↓
用户接受的当前 Version Charter / Goal Contract
    ↓
本交接包的当前事实文件
    ↓
最新完整版本化路线
    ↓
外部研究、本地参考项目与用户笔记
    ↓
Codex 推断
```

需要特别区分：

- **事实冲突**：由源码、测试、命令和已接受状态文件裁决；
- **未来路线冲突**：由最新版本化路线与用户后续决策裁决；
- **当前实施冲突**：由已接受的 Version Charter 和 Goal Contract 裁决；
- **参考实现差异**：不自动裁决项目路线，只形成适配分析。

# 6. 冲突处理规则

发现文件之间存在不一致时，不得静默选择。

必须输出：

```yaml
conflict:
  topic:
  source_A:
  source_B:
  conflict_type:
    - current_fact
    - terminology
    - future_roadmap
    - implementation_scope
    - evidence_claim
  recommended_resolution:
  requires_user_decision:
```

以下情况必须暂停并报告：

- 新路线与已接受工程事实冲突；
- V0 Charter 草案要求推翻 G001–G006 结论；
- 需要修改 Pi Core；
- 需要访问 Pi 私有接口；
- 需要让 Agent 修改 Verifier、Promotion Gate 或 Permission Upper Bound；
- 需要提前建设 V3/V4 控制平台；
- 参考项目许可证或来源不允许拟议的移植方式；
- 当前状态与 `CURRENT_STATE.md` 不一致。

# 8. 成熟上游的使用原则

成熟项目和论文不是只能“抽象借鉴”。

在许可证允许、项目确有需要、用户能够理解和解释的前提下，允许：

```yaml
allowed_reuse:
  direct_dependency: true
  module_porting: true
  cross_language_rewrite: true
  behavioral_reimplementation: true
  architecture_adaptation: true
```

但必须记录：

- 来源；
- 固定版本或 Commit；
- 许可证；
- 原模块解决的问题；
- 本项目采用、删除或修改的部分；
- 与原实现的差异；
- 在 Pi / TypeScript / Coding Agent 场景中的验证结果。

“个人贡献边界”用于准确归因，不用于追求没有必要的原创纯度。
