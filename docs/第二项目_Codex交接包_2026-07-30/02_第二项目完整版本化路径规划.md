# 1. 总体路线

第二项目不一次性实现完整自进化平台，而是沿着以下版本路线逐步升级：

```text
Phase 4：V0 Charter 与 Pi 架构冻结
    ↓
V0：可实际使用的 Coding Agent Workbench
    ↓
V1：Skill / Runtime / Verifier 分层可靠性实验
    ↓
V2：有界多路径自适应恢复
    ↓
V2.5：Fault-conditioned Failure Lab
    ↓
V3：Experience → Candidate Intervention → Regression
    ↓
V4：Experience-guided Routing 与 Policy Retirement
    ↓
V5：Godot / 游戏研发 AI 工具链扩展
```

各版本的作用：

- **V0**：让项目从 Spike 变成真实工具；
- **V1**：证明 Runtime 干预相对于 Skill 的必要性；
- **V2**：形成求职项目最重要的主动能力和甜点版本；
- **V3**：完成一条可信、受控的“自进化”最小闭环；
- **V4 以后**：作为持续升级上限，不作为求职前全部完成的硬条件。

# 2. 项目最终定位

## 2.1 推荐名称

```text
Adaptive Coding Agent Harness
```

副标题：

```text
Reliability-first Coding Agent Workbench
with bounded recovery and eval-gated experience reuse
```

中文：

> **可靠性优先的自适应 Coding Agent Harness：通过环境验证驱动有界多路径恢复，并将成功与失败轨迹转化为经过回归门禁的 Skill / Policy 候选。**

## 2.2 项目不是

- Claude Code Clone；
- Pi 的功能补全工程；
- 单纯 Trace Dashboard；
- 通用 Agent Benchmark；
- 通用 Multi-Agent 平台；
- 自动修改自身源码的开放式 Self-Evolving Agent；
- 只跑几个 A/B Case 的 Eval 脚本。

## 2.3 项目真正回答的问题

### 单次任务

> Agent 失败或结果不确定后，Harness 应该继续原 Session、重启 Session、改变 Skill、改变 Context，还是使用其他恢复策略？

### 多路径选择

> 如何在隔离 Workspace 中运行少量候选路径，并由测试、Build、Diff 和成本选择最佳结果？

### 跨任务改进

> 一次成功恢复什么时候只是偶然，什么时候有资格成为可复用的 Skill、Policy 或 Routing Rule？

# 3. 长期架构原则

## 3.1 稳定内核与可变 Scaffold 分开

### 稳定内核

早期不允许运行中的 Agent 自行修改：

```text
Pi Runtime Commit
Task Contract
Environment Identity
Verifier Contract
Run / Event Identity
Permission Upper Bound
Promotion Gate
Secret Handling
```

### 可变 Scaffold

可以形成 Candidate：

```text
Skill
Context Projection
Tool Result Policy
Recovery Policy
Session Strategy
Prompt
Workflow Fragment
Routing Rule
```

### 条件性可变

需要单独审查：

```text
Tool Wrapper
Failure Classifier
Verifier Implementation
Candidate Generator
Runtime Source Patch
```

这套分层来自自进化资料最有价值的结论：模型不变，Scaffold 仍然可以演化，但不同 Scaffold 组件的风险、可比性和批准边界不同。

## 3.2 Executor、Verifier、Curator、Promotion Gate 分权

```text
Pi Executor
负责执行 Coding Task

Verifier
负责判断环境结果

Curator
负责提出 Candidate Skill / Policy

Promotion Gate
负责决定 Candidate 是否生效
```

不得形成：

```text
Agent 自己执行
→ 自己判断成功
→ 自己总结经验
→ 自己修改 Verifier
→ 自己批准上线
```

Curator 初期不需要做成复杂独立 Agent。它可以只是一个受限 Prompt、CLI 命令和结构化输出 Schema。

## 3.3 Experience 对象不能混在一个 Markdown 中

必须区分：

```text
Raw Trace
≠ Failure Diagnosis
≠ Experience Record
≠ Candidate Intervention
≠ Active Skill / Policy
```

建议长期数据链：

```text
Run Artifact
→ Diagnosis
→ Experience
→ Candidate
→ Evaluation
→ Promotion Record
```

```text

```

# 7. V1：Skill / Runtime / Verifier 分层可靠性实验

这是项目第一次真正回答：

> 为什么不能只写一个 Skill？

## 7.1 实验组

### A：Baseline

```text
Pi Coding Agent
```

### B：Skill-only

```text
Pi
+ Reliability Skill
```

Skill 要求：

- 修改前检查工作区；
- 只修改允许路径；
- 修改后运行测试；
- 检查 Git Diff；
- 测试失败不得宣布完成；
- 输出失败状态。

### C：Skill + External Control

```text
Pi
+ 同一 Skill
+ External Verifier
+ Completion Gate
+ 一次有界 Recovery
```

## 7.2 任务设计

优先选择：

- 微型 TypeScript 仓库；
- 有明确失败测试；
- 修改范围有限；
- 禁止修改测试；
- 可确定性判断。

任务集不能只包含“很容易首次成功”的 Case，也不能为了制造失败故意设计异常任务。应同时包含：

- 正常 Coding Task；
- 容易遗漏测试的 Task；
- 容易错误声明完成的 Task；
- 修改范围约束 Task。

## 7.3 指标

```text
Verified Task Success
False Completion Rate
Test Execution Rate
Recovery Trigger Rate
Recovery Success
Forbidden Change Rate
Invalid Run Rate
Token
Latency
Cost
```

## 7.4 V1 必须回答

1. Skill 已经解决多少问题？
2. External Verifier 带来什么增量？
3. 一次 Recovery 的实际收益是什么？
4. Candidate 的成本是否可接受？
5. 哪些失败不是 Skill 问题？

## 7.5 决策

### Skill 已解决绝大多数正常任务

则 Runtime 主线收缩到：

- 故障；
- 中断；
- Context；
- Session；
- Tool；
- 外部 Outcome。

### External Control 有明显增益

Completion Verification 成为 Active Policy。

### 结果不确定

报告 `INCONCLUSIVE`，不强行 Promote。

## 7.6 Portfolio 状态

V1 是一个合格的 Reliability / Eval 项目，但仍不是项目最终亮点。

# 8. V2：有界多路径自适应恢复

这是第二项目的**简历甜点版本**。

## 8.1 核心闭环

```text
Primary Run
→ Verifier Failure
→ Minimal Failure Classification
→ Candidate Recovery Paths
→ Isolated Rollouts
→ Environment Verification
→ Best Path Selection
→ Commit Result
```

## 8.2 第一版只做两条恢复路径

### Path A：继续原 Session

```text
Same Session
+ Structured Failure Packet
+ One Recovery Budget
```

### Path B：干净 Session 重启

```text
New Session
+ Original Task
+ Failure Packet
+ test-first / minimal-patch Skill
+ relevant file context
```

暂时不需要同时做五条路径。

## 8.3 为什么这两条最有价值

它们比较的是一个真实 Harness 决策：

```text
保留已有上下文和推理
vs
放弃错误假设，重新开始
```

这比简单更换 Prompt 更有 Runtime 含量。

## 8.4 Failure Packet

不应把整条 Trace 全部塞回模型。

建议包含：

```yaml
failure_packet:
  task:
  verifier_failures:
  changed_files:
  forbidden_changes:
  failing_commands:
  relevant_logs:
  prior_attempt_summary:
  critical_constraints:
```

## 8.5 Workspace 隔离

优先比较：

- 临时副本；
- Git Worktree。

V2 至少要保证：

- 两条路径从同一失败状态开始；
- 修改互不污染；
- 最佳路径可单独保留；
- 未选路径可清理。

## 8.6 Path Score

先硬门：

```text
Verifier Valid
Tests Pass
Build Pass
No Forbidden Changes
```

多条都通过时再比较：

```text
Token
Latency
Tool Calls
Diff Size
Warnings
Side-effect Risk
```

不得因为成本低而选择未通过任务的路径。

## 8.7 初期 Candidate 来源

第一版采用固定策略库：

```text
continue_session
clean_restart_with_failure_packet
```

之后再增加：

```text
compact_context
test_first_skill
minimal_patch_skill
different_thinking
different_model
```

暂时不让 LLM 任意生成无限 Candidate。

## 8.8 V2 的核心指标

```text
Adaptive Recovery Success
Best-of-N Gain
Recovery Cost
Wrong-path Selection Rate
Unnecessary Branch Rate
```

## 8.9 两个必须展示的案例

### 正例

Primary Run 失败，至少一条 Recovery 成功，系统选择正确结果。

### 反例

Primary Run 首次通过，系统不创建无意义分支。

这证明它不是无脑烧 Token 的 Best-of-N。

## 8.10 Portfolio 状态

V2 完成后，项目可以准确表述为：

> 环境反馈驱动的 Adaptive Coding Agent Harness，能够在失败后比较继续 Session 与干净重启等恢复路径，并依据测试、Build、Diff 与成本选择最佳结果。

这是求职前最重要的核心版本。

# 9. V2.5：Fault-conditioned Failure Lab

V2 已有多路径后，再加入少量真正需要 Runtime 控制的故障。

## 9.1 首批建议只选两到三种

### Long-running Shell Timeout / Cancellation

验证：

- Timeout 后子进程是否仍运行；
- 端口和文件副作用是否持续；
- 是否可以安全 Recovery。

### Oversized Tool Result / Context Pressure

验证：

- Skill 约束是否丢失；
- Tool Result 外置 + 摘要 + 引用是否更好；
- Context Strategy 是否应切换。

### Session Restart / Side-effect Reconciliation

只有出现真实可复现 Case 后进入：

```text
Tool 已修改 Workspace
→ Result 未持久化
→ Resume 是否重复修改
```

不需要先建设通用 Exactly-once 平台。

## 9.2 实验输出

- Task Failure；
- Agent Failure；
- Infrastructure Invalid；
- Recovery Path；
- Fault-conditioned Success；
- Side-effect Evidence。

## 9.3 价值

这一版本能证明：

> Skill 适合指导正常流程，但 Tool Timeout、Context Overflow、Session/Side Effect 等问题必须由 Harness 层处理。

# 10. V3：Experience → Candidate Intervention → Regression

这是最小可信 H3，即跨任务经验复用。

## 10.1 Experience Pipeline

```text
Run Trace + Outcome + Diff
→ Failure Diagnosis
→ Experience Record
→ Candidate Intervention
```

## 10.2 Curator 形式

推荐 C2：

```text
结构化 LLM Curator
+ 固定输入 Schema
+ 固定输出 Schema
+ 无直接发布权限
```

它可以提出：

- Skill；
- Recovery Policy；
- Context Policy；
- Tool Policy；
- Routing Rule。

## 10.3 Candidate Intervention Schema

```yaml
candidate:
  candidate_id:
  type:
  target_failure:
  source_runs:
  applicability:
  proposed_change:
  expected_effect:
  known_risks:
  status: proposed
```

## 10.4 Related Task Stream

不能只在原任务上重跑。

至少包含：

```text
T1：暴露失败的原任务
T2：同 Failure Family、不同代码结构
T3：Held-out Related Task
T4：Unrelated Task，检查负迁移
```

可选：

```text
T5：环境轻微变化，检查适用边界
```

## 10.5 Promotion Lifecycle

```text
proposed
→ dev_validated
→ regression_passed
→ approved
→ active
→ deprecated
→ rolled_back
```

## 10.6 Promotion Gate

检查：

- Related Task 是否改善；
- Held-out 是否改善；
- 无关任务是否退化；
- 成本是否上升；
- 是否与已有 Skill 冲突；
- 是否只记住原任务。

## 10.7 最小完成标准

不需要建完整 SkillOS。

只需完成一条真实闭环：

```text
一次真实失败
→ 一条成功 Recovery
→ 一个 Candidate Skill / Policy
→ Related Task 验证
→ Unrelated Regression
→ 人工 Promote 或 Reject
```

## 10.8 Portfolio 状态

完成 V3 后可以谨慎表述：

> 将成功与失败轨迹转化为经过相关任务和回归验证的 Harness Intervention 候选，并支持晋级、拒绝和回滚。

比直接写“自进化 Agent”更可信。

# 11. V4：Experience-guided Routing 与 Harness Retirement

这一版本需要 V2/V3 已经积累足够数据。

## 11.1 Routing

根据：

- Failure Family；
- Repository；
- Model；
- Thinking；
- Task Type；
- 历史 Recovery Success；

决定：

- 是否继续 Session；
- 是否新 Session；
- 使用哪个 Skill；
- 是否启用多路径；
- 使用哪个 Context Policy。

## 11.2 初期不要训练模型

优先顺序：

```text
显式规则
→ 统计优先级
→ 简单可解释 Router
→ 数据足够后再考虑学习型 Router
```

## 11.3 Policy / Skill Retirement

记录：

- 使用次数；
- 成功率；
- 成本；
- Negative Transfer；
- 适用模型；
- 长期未使用；
- 与新 Policy 冲突。

生命周期：

```text
active
→ candidate_for_retirement
→ retired
```

## 11.4 Harness Assumption Registry

每条 Scaffolding 回答：

- 为什么存在；
- 解决什么 Failure；
- 来源 Run；
- 哪些模型需要；
- 哪些模型已经不需要；
- 什么条件下删除。

## 11.5 Meta-Evaluation

只评估改进器，不做完整 Meta-Agent：

- Curator 误诊率；
- 重复 Candidate 率；
- 有害 Candidate 率；
- Promotion 后回滚率；
- Registry 膨胀；
- 无效 Skill 数量。

# 17. 必须避免的实现偏差

## 17.1 不要把 V0 建成大平台

不优先：

- Web Dashboard；
- SQLite 数据平台；
- 多租户；
- 大量 Inspector；
- 复杂配置 UI。

## 17.2 不要让所有风险变成 Goal

只有会改变当前架构、有真实证据且无法后移的问题才进入 Goal。

## 17.3 不要把多路径变成无脑 Best-of-N

必须：

- Failure 触发；
- Candidate 有界；
- 成本记录；
- 首次成功时不分支。

## 17.4 不要把 Experience 变成无限追加 Skill

需要：

- applicability；
- source runs；
- related task；
- regression；
- delete / retire。

## 17.5 不要把自进化写成自动修改源码

至少求职前，自进化对象应主要是：

- Skill；
- Policy；
- Context；
- Routing。

## 17.6 不要让 Agent 修改 Verifier 和 Promotion Gate

这是受保护边界。

# 18. 推荐的 Goal 治理方式

## 18.2 每个 Goal 必须有

- 证据；
- 输入；
- 输出；

## 18.3 不需要

- 每个小风险一个 ADR；
- 每个普通依赖一份报告；
- 每个未验证点一个正式 Gate。

# 20. 最终判断

第二项目最合适的长期身份不是：

```text
Pi Reliability Eval Platform
```

也不是：

```text
开放式 Self-Evolving Coding Agent
```

而是：

> **一个可靠性优先、环境反馈驱动、能够进行有界多路径恢复，并将经过验证的恢复经验逐步沉淀为 Skill、Policy 和 Routing 能力的 Adaptive Coding Agent Harness。**

这条路线同时满足：

- 当前 Pi 与 G001–G006 的真实工程基础；
- `cc-harness-knowledge` 的学习转化；
- Skill / Runtime 边界；
- 多路径主动能力；
- 自进化资料中的 Experience、Curator、Related Task 和 Promotion 思想；
- TypeScript、Coding Agent、Tool、Context、Session、Trace、Eval、Fault、Recovery 和游戏 AI 工具链的简历技术栈需求。
